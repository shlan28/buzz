# Buzz 客户端 UI 设计规范

> 更新日期：2026-07-31
> 更新说明：首次从 Desktop 与 Mobile 的现有实现中提炼产品级设计原则、设计 token、交互模式和新功能验收清单。

## 1. 规范的目的

这份规范用于回答一个具体问题：**Buzz 新功能应该怎样设计，才能看起来、用起来仍然是 Buzz？**

适用范围：

- Desktop：Tauri + React + Tailwind + shadcn/ui；
- Mobile：Flutter + Material 3；
- 同时覆盖人类用户、Agent、工作流、项目与社区管理界面；
- 约束产品结构和交互意图，不替代平台代码规范。

事实源：

- Desktop 主题与 token：`desktop/src/shared/styles/globals/theme.css`、`desktop/tailwind.config.js`；
- Desktop 基础组件：`desktop/src/shared/ui/`；
- Mobile 主题与 token：`mobile/lib/shared/theme/`；
- 平台架构约束：`AGENTS.md`、`desktop/README.md`、`mobile/README.md`。

## 2. 产品设计原则

### 2.1 人与 Agent 是同一空间的一等成员

Agent 不应被设计成附属机器人面板。身份、头像、状态、消息、权限和操作历史应尽量复用成员模型；只有 Agent 独有的运行状态、模型、工具调用和控制动作才增加专属表达。

设计判断：

- 能复用“成员 / 消息 / 频道 / 活动”模式时，不新建 Agent 专用模式；
- Agent 正在工作、等待、失败、需审批必须可辨认；
- 高风险 Agent 操作必须展示作用对象、范围和结果；
- 人类与 Agent 产生的内容保持同一信息层级，差异通过身份与状态表达。

### 2.2 社区是最高层用户边界

社区不是普通筛选器，而是身份、频道、缓存和连接状态的边界。切换社区后，界面必须明确告诉用户“现在在哪里”，并避免旧社区状态泄漏。

- 全局导航始终提供社区上下文；
- 社区切换属于环境切换，不应伪装成普通 tab；
- 连接、重连、离线与权限问题应在当前社区语境中解释；
- 新增模块级缓存时必须遵守 `resetCommunityState()` 约束。

### 2.3 会话是主工作面，工具是上下文面板

Buzz 的中心是频道、线程、DM 与活动记录。搜索、成员、Agent 会话、媒体评论、项目详情等是围绕当前对象展开的辅助面。

- 主内容区保留当前会话或任务；
- 临时查看优先使用右侧辅助面板，避免打断上下文；
- 创建、确认、少量字段编辑用 dialog / sheet；
- 长流程、强导航任务使用独立页面；
- 不把同一层级的功能混合成无限嵌套弹窗。

### 2.4 可追溯优先于“神奇自动化”

Buzz 的价值来自签名事件、统一日志与可搜索历史。自动化界面必须让用户看到触发、执行、审批、结果和失败。

- 状态文案回答“发生了什么”和“接下来怎么办”；
- 操作完成后提供可定位的结果，而不只显示 toast；
- 破坏性或不可逆动作要求明确对象与影响范围；
- 进度不是装饰：未知进度用 indeterminate，已知步骤显示阶段。

### 2.5 密度高，但层级要安静

Buzz 是长期工作的桌面工具，不是营销页面。依靠排版、间距、语义色和局部表面建立层级，避免大量高饱和色、重阴影和重复边框。

- 常态内容以中性色为主；
- 主色只强调选中、主要动作、焦点和关键身份；
- 卡片默认扁平，阴影只表达浮层或空间分离；
- 元信息比正文弱一级，但不能牺牲可读性。

## 3. 信息架构与布局

### 3.1 Desktop

推荐骨架：

1. 社区 / 全局入口；
2. 左侧 sidebar：频道、DM、项目与主要导航；
3. 主内容区：当前频道、页面或工作对象；
4. 可选辅助面板：线程、成员、Agent 会话、媒体评论或详情；
5. 短暂浮层：菜单、popover、tooltip、dialog。

规则：

- 页面本身不滚动，滚动属于明确的内容容器；
- sidebar 项目选中、hover、未读、静音、断线状态必须可区分；
- 辅助面板应保留主内容上下文，并有明确关闭/返回动作；
- 当宽度不足以同时容纳主区和辅助面板时，辅助面板切换为覆盖层或独立视图；
- 不在主内容区同时制造两个竞争性的一级标题和主要 CTA。

### 3.2 Mobile

推荐骨架：

- 一级目的地使用底部导航；
- 页面级上下文使用透明、无 elevation 的 app bar；
- 长列表与会话占据完整主视图；
- 次级操作使用 bottom sheet；
- 需要完成且必须聚焦的任务使用全屏页或 dialog；
- 返回行为遵循平台栈，不复制 Desktop 的多栏布局。

移动端不是桌面的缩小版。功能语义一致，但交互结构允许平台化：

| 目的 | Desktop | Mobile |
|---|---|---|
| 线程 / 详情 | 右侧辅助面板 | 新页面或 sheet |
| 次要动作 | popover / menu | bottom sheet |
| 主导航 | sidebar | bottom navigation / 页面栈 |
| 悬停信息 | tooltip + hover | 显式标签或长按菜单 |
| 多栏比较 | 并列区域 | 分步或可切换视图 |

## 4. 视觉语言

### 4.1 颜色

Buzz 默认基于 Catppuccin Latte / Macchiato，并通过语义 token 消费颜色。组件不得把主题色的具体 HSL/HEX 当成产品语义。

核心语义：

- `background / foreground`：应用基底与主文本；
- `card / popover`：内容表面与浮层；
- `primary`：主操作、焦点、选中；
- `secondary / muted`：次级表面与弱信息；
- `accent`：交互反馈，不等于第二主色；
- `destructive`：删除、撤销不了的拒绝或危险动作；
- `border / input / ring`：边界、输入和键盘焦点；
- `status.added / deleted / modified`：diff 语义；
- `warning`：可恢复风险或需要注意；
- `sidebar.*`：侧栏专属语义。

使用规则：

- 文本与图标只使用语义前景色；
- 成功、警告、失败不能只靠颜色，必须搭配图标或文字；
- disabled 通过透明度、前景和交互状态组合表达，不能伪装成正常按钮；
- 自定义主题必须保证所有语义角色都有明暗模式；
- 仅品牌插画、媒体内容或受控可视化允许直接色值。

### 4.2 字体与层级

统一字体为 Inter；系统 fallback 由平台主题维护。

Desktop：

- 聊天正文和作者：`text-base`，作为产品基准字号；
- 辅助正文：`text-sm`；
- 标签与小型控制：`text-xs`；
- 时间戳、计数、追踪标签：`text-2xs`；
- 极小 glyph / micro label：`text-3xs`；
- 页面大标题仅使用已有 `text-title` 等命名 token。

Mobile：

- 使用 `context.textTheme` / `textTheme`；
- 会话正文以 16sp 为基准；
- 次级元信息用 12–14sp；
- 标题依层级使用 `title*` / `headline*`；
- 不在业务 widget 中发明孤立字号。

硬规则：

- Desktop 可读文字必须使用 rem token，不得使用任意 px/rem 字号；
- Mobile 不直接复制 Desktop class，应映射到 TextTheme 角色；
- 一块内容最多形成 3 个明显文字层级；
- 正文链接、code、mention 和状态文本必须仍能随缩放正常工作。

### 4.3 间距

以 4px 基础节奏组织空间。

Mobile 已定义：

`2 / 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64 / 80`

推荐语义：

- 2–4：图标内部校准、紧密 metadata；
- 8：同一控件内元素；
- 12：紧凑列表项内部；
- 16：标准控件 padding、同组元素；
- 20：页面内容 gutter；
- 24：卡片/section 间；
- 32+：页面主要区域分隔。

规则：

- 新功能先复用现有 Grid / Tailwind scale；
- 同一父容器只选择一种主要纵向节奏；
- 用 gap / padding 建立关系，不用空白字符和无语义空容器；
- 列表密度可以紧凑，但可点击目标不能随之缩小到不可操作。

### 4.4 圆角、边框与阴影

基础圆角与 Desktop shadcn New York 风格对齐：

- `xs = 4px`：紧凑小元素；
- `sm = 6px`；
- `md = 8px`：按钮、输入；
- `lg = 10px`：常规卡片；
- `card = 12px`：组合设置卡片；
- `dialog = 24px`：对话框；
- `full`：头像、badge、pill。

规则：

- 卡片默认无 elevation；
- 边框用于结构分组，不给每一层都加边框；
- 阴影仅用于 popover、dialog、辅助面板等确实高于当前平面的内容；
- 同一组件不可同时使用重边框、重阴影和强背景三种强调；
- 嵌套容器的圆角应逐级减小或由外层统一裁切。

### 4.5 图标与媒体

- 图标表达动作或对象，不能替代不明确的业务词；
- 仅图标按钮必须有 accessible name 和 tooltip（Desktop）；
- 常规控制统一视觉尺寸，默认 16–20，主导航 24；
- 头像、社区图标和 Agent 身份图像必须有加载、缺失和错误 fallback；
- 媒体保持比例，加载过程使用 skeleton，失败状态提供重试或替代操作。

## 5. 核心组件规范

### 5.1 按钮

层级：

- Primary / Filled：当前范围内唯一主要提交动作；
- Secondary / Outline：并列但较弱动作；
- Ghost / Text：工具栏、列表行和低强调动作；
- Destructive：删除、移除、拒绝等危险动作；
- Icon button：含义稳定、空间受限的通用动作。

一个 dialog footer 通常只有一个 primary。危险操作不能仅通过按钮颜色解释风险。

状态：default、hover/pressed、focus-visible、loading、disabled。loading 时保持宽度，阻止重复提交，并用文字说明正在做什么。

### 5.2 输入与表单

- label 常驻，不以 placeholder 代替；
- helper 解释格式，error 解释如何修复；
- 同一表单按用户任务分组，不按后端对象字段顺序排列；
- 保存失败保留用户输入；
- 远程校验显示进行中与失败；
- 密钥、token、邀请链接等敏感信息默认遮挡，并提供明确复制反馈。

### 5.3 列表、卡片与表格

- 同类可扫描记录优先列表；
- 卡片用于有独立身份、多个字段和局部动作的对象；
- 表格仅用于字段固定、需要横向比较的数据；
- 整行可点击时，行内按钮必须避免触发父级导航；
- 列表项的主信息、次信息、状态、操作位置保持稳定；
- 空列表必须说明它代表“尚未创建”“被过滤为空”还是“加载失败”。

### 5.4 Dialog、Popover 与辅助面板

- dialog：创建、确认、短表单；
- alert dialog：明确危险后果的确认；
- popover/menu：短暂选择和局部动作；
- 辅助面板：需要持续参照主内容的详情；
- 独立页面：复杂配置、跨 section 流程、需要深链接的内容。

禁止：

- dialog 中再打开同级 dialog；
- 用 tooltip 承载完成任务所需的信息；
- 用 toast 作为唯一错误恢复路径；
- 用 popover 容纳长表单或大量滚动内容。

### 5.5 会话、线程和活动

- 作者、时间、正文是基本层级；
- 编辑、回复、reaction、附件、Agent 状态是附加层；
- 连续消息应降低重复身份噪音，但不能丢失归属；
- thread 必须保留根消息语境；
- 未读定位、跳转到底部、新消息提示不可互相遮挡；
- 系统事件和工作流事件应比用户消息更紧凑，但必须可展开查看证据。

## 6. 状态与反馈

每个异步功能至少设计以下状态：

1. 初始；
2. 加载；
3. 成功且有数据；
4. 成功但为空；
5. 可恢复错误；
6. 权限不足；
7. 离线 / 重连；
8. 提交中；
9. 部分成功或数据过期（如适用）。

反馈层级：

- 控件内：即时校验、loading；
- 内容区内：空态、错误、重试；
- toast：短暂确认，不承载关键决策；
- banner / connection card：持续影响当前范围的问题；
- dialog：需要用户确认或阻止继续的风险。

Skeleton 应模拟最终结构；不要用全屏 spinner 掩盖仍可使用的其他区域。

## 7. 交互、键盘与无障碍

- 所有 Desktop 核心操作可通过键盘完成；
- focus-visible 必须清晰，不能只依赖浏览器默认偶然表现；
- Esc 关闭临时浮层，不能破坏已经提交的状态；
- Tab 顺序与视觉顺序一致；
- 菜单、tab、dialog 使用正确语义与 aria 状态；
- 点击/触摸目标推荐至少 44×44pt；紧凑 Desktop 控件需保留足够命中区；
- 图标、状态点和颜色编码必须有文本替代；
- 尊重 reduced motion；
- 动画用于解释出现、移位、展开和反馈，通常保持在 120–240ms；
- 直播消息、状态变化和错误提示应选择合适的 live region，避免重复播报。

## 8. 新功能设计流程

### 8.1 设计前

- 写清用户、目标、入口、完成条件；
- 判断属于社区、频道、线程、成员、Agent、项目还是全局设置；
- 找出可复用的既有模式与组件；
- 列出所有异步、权限、离线和空态；
- 判断 Desktop 与 Mobile 是同构还是平台化表达。

### 8.2 设计中

- 先画信息层级和状态流，再选视觉组件；
- 使用语义 token，不使用主题具体颜色；
- 保持一个范围内只有一个主要 CTA；
- 给危险操作写清对象与后果；
- 给 Agent/工作流行为设计可追溯结果；
- 验证缩放、窄宽、长文案、多语言和超长名称。

### 8.3 实现映射

Desktop：

- 优先复用 `desktop/src/shared/ui/`；
- 业务 UI 放入对应 `desktop/src/features/<feature>/`；
- 字体、颜色和圆角来自 Tailwind/theme token；
- 页面滚动锁与辅助面板使用 shared layout 机制；
- 新的 community-scoped singleton 必须接入 reset。

Mobile：

- 使用 `HookConsumerWidget` / `ConsumerWidget`，不得新增 `StatefulWidget`；
- 使用 `context.colors`、`context.textTheme`、`Grid`、`Radii`；
- feature 不跨 feature import，只通过 `shared/` 复用；
- 一个 public widget 一个文件，复杂私有 widget 拆入 sibling part；
- 使用平台导航、sheet 与触控语义。

## 9. 设计验收清单

### 产品一致性

- [ ] 用户能说清当前社区、频道/对象和正在执行的动作。
- [ ] 人与 Agent 复用共同身份和协作模型，差异只表达必要能力。
- [ ] 自动化结果可定位、可追溯，不只给“成功”提示。
- [ ] 新功能没有创建与既有频道、成员、项目、Agent 重复的概念。

### 结构与组件

- [ ] 选择了正确容器：页面、辅助面板、dialog、sheet 或 popover。
- [ ] 一个范围只有一个 primary CTA。
- [ ] 复用了 shared 组件与既有布局模式。
- [ ] 没有 dialog 套 dialog、长表单塞 popover、tooltip 承担关键说明。

### 视觉

- [ ] 仅使用语义颜色和命名字体 token。
- [ ] Desktop 文本可随 Cmd +/- 缩放。
- [ ] 间距、圆角、边框和阴影来自既有尺度。
- [ ] 明暗主题、长文本、空内容和高密度数据均可读。

### 状态与风险

- [ ] loading、empty、error、permission、offline、submitting 都有设计。
- [ ] 提交失败保留输入，重复提交被阻止。
- [ ] destructive 操作说明对象、影响和可恢复性。
- [ ] 连接或数据过期不会被误呈现为“没有内容”。

### 可访问性与平台

- [ ] 键盘、焦点、Esc、Tab 顺序正确。
- [ ] 仅图标操作有 accessible name。
- [ ] 状态不只依赖颜色，触控目标足够大。
- [ ] reduced motion、缩放、窄宽/手机布局可用。
- [ ] Desktop 与 Mobile 保持同一功能语义，但遵循各自导航习惯。

## 10. Constructive suggestion：下一步把“规范”变成可验证资产

当前规范仍主要依赖人工评审。建议后续单独立项：

1. 为 Desktop shared UI 与 Mobile theme 建一个跨平台 token 对照页；
2. 为按钮、输入、列表、dialog、空态和连接状态建立截图基线；
3. 在 PR 模板加入本文件第 9 节的简版检查项；
4. 为颜色对比、任意字号、focus、可访问名称和主题截图增加自动检查；
5. UI 规范发生变化时，同时更新 token、示例与截图，避免文档和实现分叉。
